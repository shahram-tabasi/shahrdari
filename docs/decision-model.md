## ۱. ساختار معیارها

شیوه‌نامه معیارها را به دو خانواده تقسیم می‌کند و سامانه همین تفکیک را در کد
حفظ کرده است (`backend/src/data/criteria.js`):

| خانواده | تعداد | ماهیت | محل اعمال |
|---|---|---|---|
| معیارهای الزامی | ۱۲ گیت | صفر و یک | فیلتر شماره یک |
| معیارهای ترجیحی | ۳۷ معیار در ۸ بعد | طیفی | فیلتر شماره دو و سه |

### ۱-۱. ابعاد و وزن پیش‌فرض

شیوه‌نامه برای هر بعد یک **رتبه** تعیین کرده اما وزن عددی نداده است. برای
اینکه وزن‌ها قابل ردیابی به سند بمانند، وزن پیش‌فرض با روش **مرکز ثقل رتبه‌ای
(Rank-Order Centroid)** از همان رتبه‌ها استخراج می‌شود:

```
w(i) = (1 / n) · Σ (j = i .. n) 1 / j
```

که در آن `n = ۸` و `i` رتبه بعد است. این وزن، مرکز ثقل فضای همه بردارهای وزنی
سازگار با ترتیب اعلام‌شده است؛ یعنی کم‌ادعاترین انتخابی که با سند نمی‌جنگد.

| رتبه | بعد | وزن پیش‌فرض (٪) |
|---|---|---|
| ۱ | اجتماعی | ۳۳٫۹۷ |
| ۲ | مالی | ۲۱٫۴۷ |
| ۳ | زیست‌محیطی | ۱۵٫۲۲ |
| ۴ | فنی | ۱۱٫۰۶ |
| ۵ | اقتصادی | ۷٫۹۳ |
| ۶ | سازمانی (سیاسی) | ۵٫۴۳ |
| ۷ | ریسک | ۳٫۳۵ |
| ۸ | رقابتی | ۱٫۵۶ |

این وزن‌ها **پیش‌فرض** هستند، نه قطعی: پنل خبرگان می‌تواند آن‌ها را مستقیم یا
از راه ماتریس مقایسات زوجی (AHP) بازنویسی کند.

### ۱-۲. جهت معیارها

هر معیار `direction` دارد: `benefit` (بیشتر بهتر) یا `cost` (بیشتر بدتر).
معکوس‌سازی معیارهای هزینه‌ای در **موتور نرمال‌سازی** انجام می‌شود، نه در داده.
دلیل: اگر داده از پیش معکوس ثبت شود، جهت معیار در جایی که قابل بازبینی است
ثبت نمی‌شود و یک اشتباه ثبت داده می‌تواند بی‌سروصدا ترجیح را برعکس کند.

## ۲. موتور وزن‌دهی — شاخص سازگاری

`backend/src/domain/weighting.js`

سه منبع وزن پشتیبانی می‌شود:

1. **ROC** از رتبه‌های شیوه‌نامه (پیش‌فرض، بدون نیاز به جلسه خبرگان)
2. **وزن مستقیم** از تحلیلگر (اسلایدرهای رابط کاربری)
3. **AHP** از ماتریس مقایسات زوجی خبرگان

برای AHP، بردار اولویت با میانگین سطری ماتریسِ ستونی‌نرمال‌شده تخمین زده
می‌شود و سپس:

```
λmax = Σ (جمع ستون i × اولویت i)
CI   = (λmax − n) / (n − 1)
CR   = CI / RI(n)
```

`RI` شاخص تصادفی ساعتی است. اگر `CR > 0.1` ماتریس **ناسازگار** علامت می‌خورد و
هشدار آن همراه نتیجه برمی‌گردد؛ نتیجه پنهان نمی‌شود اما بدون برچسب هم عرضه
نمی‌شود.

### ۲-۱. تبدیل وزن بعد به وزن معیار

وزن سراسری هر معیار برگ:

```
globalWeight(c) = dimensionWeight(dim(c)) × localWeight(c) / Σ localWeight(dim(c))
```

بدین ترتیب پنل خبرگان روی ۸ اسلایدر کار می‌کند، در حالی که ارزیابی روی ۳۷
معیار انجام می‌شود.

## ۵. موتور رتبه‌بندی — PROMETHEE II

`backend/src/domain/promethee.js`

شیوه‌نامه ماژول رتبه‌بندی را «محاسبه **جریان‌ها** و رتبه پروژه‌ها» تعریف کرده
است. مجموع وزنی ساده سه چیزی را که پیوست شماره دو می‌خواهد نمی‌دهد و به همین
دلیل کنار گذاشته شد:

- **آستانه ترجیح**: اختلاف ناچیز بین دو پروژه نباید به ترجیح تبدیل شود.
- **جریان‌های زوجی**: بدون آن، «بررسی رتبه‌برگشتی» و «آزمون ورود و حذف پروژه»
  آزمون‌های بی‌معنایی می‌شوند.
- **تفکیک علت برتری**: گزارش رسمی باید بگوید چرا پروژه الف بر ب برتری دارد.

### ۵-۱. تابع ترجیح

تابع خطی با آستانه بی‌تفاوتی `q` و آستانه ترجیح `p` (نوع پنجم برانس):

```
P(d) = 0                    اگر d ≤ q
P(d) = (d − q) / (p − q)    اگر q < d < p
P(d) = 1                    اگر d ≥ p
```

که `d = g(a) − g(b)` روی مقیاس جهت‌دهی‌شده است.

### ۵-۲. جریان‌ها

```
π(a, b) = Σ_c  ( w(c) / Σw ) · P_c( g_c(a) − g_c(b) )

φ⁺(a) = ( 1 / (n−1) ) · Σ_{b ≠ a} π(a, b)      جریان مثبت
φ⁻(a) = ( 1 / (n−1) ) · Σ_{b ≠ a} π(b, a)      جریان منفی
φ(a)  = φ⁺(a) − φ⁻(a)                           جریان خالص
```

رتبه بر اساس `φ` نزولی تعیین می‌شود. `finalScore` صرفاً نگاشت `φ ∈ [−1, 1]` به
بازه ۰ تا ۱۰۰ برای نمایش است. مقدار `utility` (مجموع وزنی) نیز به عنوان عدد
مرجع آشنا برگردانده می‌شود اما **ترتیب را تعیین نمی‌کند**.

> نکته: اگر یک طبقه فقط یک عضو داشته باشد، جریان خالص آن صفر است
> (`finalScore = 50`). این درست است، نه خطا: یک پروژه با هیچ‌کس مقایسه نشده.

## ۶. ارزیابی آینده‌نگر پروژه‌های نیمه‌تمام

`backend/src/domain/lifecycle.js`

نکته ۱ پیوست شماره دو خطای «هزینه ازدست‌رفته» را صریحاً نام می‌برد. پیامد آن در
کد مشخص است: **درصد پیشرفت و پول خرج‌شده در تصمیم ادامه/توقف وارد نمی‌شوند.**
آنچه وارد می‌شود مقایسه نهایی‌ای است که هنوز پیش روی تصمیم‌گیرنده باز است:

```
منفعت آتی   = PV(منافع قابل تحقق, زمان بهره‌برداری) × (1 − ریسک استهلاک)
هزینه آتی   = PV(هزینه تکمیل, نیمهٔ زمان تکمیل) + PV(هزینه بهره‌برداری, زمان بهره‌برداری)
هزینه توقف  = هزینه خاتمه + خسارت احتمالی

ارزش ادامه = منفعت آتی − هزینه آتی
ارزش توقف  = − هزینه توقف
```

توصیه از مقایسه این دو حاصل می‌شود. مقدار `sunkCostExcluded` صرفاً **گزارش**
می‌شود تا بازبین ببیند که عمداً کنار گذاشته شده است.

تعدیل و تنزیل:

```
escalate(amount, year) = amount × (1 + نرخ تعدیل) ^ (year − سال پایه)
PV(amount, months)     = amount / (1 + نرخ تنزیل) ^ (months / 12)
```

## ۷. عدالت فضایی و شاخص محرومیت

`backend/src/domain/equity.js`

شاخص محرومیت از **ده شاخص خام** پیوست شماره دو بازمحاسبه می‌شود، نه از یک عدد
ذخیره‌شده. هر شاخص ابتدا کمینه-بیشینه نرمال می‌شود، سپس بر اساس جهت آن
جهت‌دهی:

```
normalized(i) = (x(i) − min) / (max − min)
oriented(i)   = 1 − normalized(i)   اگر شاخص «برخورداری» باشد
oriented(i)   = normalized(i)       اگر شاخص «محرومیت» باشد

deprivationIndex = Σ oriented(i) · weight(i) / Σ weight(i)
```

شاخص منطقه، میانگین وزنی جمعیتیِ محلات آن است. منطقه‌ای که شاخص آن از آستانه
(پیش‌فرض ۰٫۶) بگذرد «منطقه هدف» است و حداقل سهم بودجه به آن تعلق می‌گیرد.

## ۸. موتور بهینه‌سازی سبد

`backend/src/domain/portfolio.js`

> «رتبه بالاتر یک پروژه الزاماً به معنای عضویت آن در سبد نهایی نیست؛ زیرا ممکن
> است ترکیب چند پروژه با رتبه‌های پایین‌تر، ارزش بیشتر، پوشش عادلانه‌تر یا
> امکان اجرای بهتری ایجاد کند.»

بنابراین انتخاب سبد یک مسئله **ترکیبی** است، نه پیمایش حریصانه فهرست رتبه.
الگوریتم: ساخت حریصانهٔ تصادفی‌شده + جست‌وجوی محلی با حرکات افزودن، حذف و
**تعویض**. حرکت تعویض همان چیزی است که اجازه می‌دهد دو پروژه ارزان‌تر جای یک
پروژه گران‌ترِ بالاتررتبه را بگیرند.

### ۸-۱. تابع هدف

```
value(S)   = Σ_{p ∈ S} Σ_o ( w(o) / Σw ) · oriented(o, p)
penalty(S) = Σ_{v ∈ violations(S)} base · (1 + magnitude(v) × 4)
objective  = value(S) − penalty(S)
```

`magnitude` نسبت تخطی به حد مجاز است. بدون آن، جریمهٔ ثابتِ هر تخطی باعث
می‌شود سبدی که یک‌بار از سقف بودجه گذشته، افزودن پروژه بعدی برایش رایگان
باشد — یعنی جست‌وجو از ناحیه شدنی فرار کند.

### ۸-۲. خانواده‌های محدودیت

| خانواده | نمونه قواعد |
|---|---|
| مالی | سقف کل، بودجه هر سال، سقف هر منطقه، تعهدات آتی، بودجه‌های غیرقابل‌انتقال، ترکیب منابع داخلی/خارجی، حداقل و حداکثر سهم هر حوزه |
| وابستگی | پیش‌نیازی، ناسازگاری، «حداقل یکی از» |
| عدالت منطقه‌ای | حداقل سهم مناطق هدف |
| ظرفیت اجرایی | ظرفیت هم‌زمان، نظارت، پیمانکار، تملک زمین، آمادگی مجوزها |
| سیاستی | حداقل سهم ایمنی و حمل‌ونقل عمومی، حداقل پروژه محله‌محور، سقف پروژه‌های فاقد طرح اجرایی، الزام تکمیل پروژه‌های پیشرفت‌بالا، سقف پروژه‌های کم‌اثر |

### ۸-۳. ناشدنی بودن

اگر هیچ ترکیبی همه محدودیت‌ها را برآورده نکند، پاسخ `status: "infeasible"`
است و فهرست پروژه‌ها **تشخیصی** است نه پیشنهاد. سامانه علاوه بر آن با
دوبخشی‌سازی روی سقف بودجه، **کمینه بودجه شدنی** را گزارش می‌کند.

### ۸-۴. تکرارپذیری

مولد اعداد تصادفی درون‌سامانه‌ای و **دانه‌دار** است (`seed` ورودی API). یک سبد
پیشنهادی باید ماه‌ها بعد عیناً بازتولید شود؛ با `Math.random` این ممکن نبود.

## ۹. تحلیل حساسیت و پایداری

`backend/src/domain/sensitivity.js`

هر سناریو **کل خط لوله** را دوباره اجرا می‌کند (وزن‌دهی، رتبه‌بندی، بهینه‌سازی).
تحلیل حساسیتی که وزن‌ها را تغییر دهد ولی رتبه‌بندی پایه را دوباره استفاده کند،
چیزی را اندازه نمی‌گیرد.

خروجی‌های هر پروژه، مطابق فهرست پیوست شماره دو:

| خروجی | روش محاسبه |
|---|---|
| درصد سناریوهای انتخاب | نسبت سناریوهایی که پروژه در سبد آن‌ها بوده |
| حداقل بودجه لازم برای ورود | دوبخشی‌سازی روی سقف بودجه |
| حساسیت به تغییر وزن‌ها | میانگین جابه‌جایی رتبه تحت اغتشاش ±۳۵٪ وزن |
| حساسیت به آستانه‌های ترجیح | میانگین جابه‌جایی رتبه تحت اغتشاش ±۵۰٪ آستانه |
| حساسیت به افزایش هزینه | **افت عضویت در سبد** به ازای واحد افزایش هزینه |
| پروژه جایگزین | پرتکرارترین پروژه‌ای که در غیاب این پروژه وارد سبد می‌شود |
| علت اصلی حذف یا انتخاب | قاعده مقیدکننده، از خروجی موتور بهینه‌سازی |

> نکته: حساسیت هزینه بر پایه **عضویت** سنجیده می‌شود نه رتبه. PROMETHEE روی
> عملکرد معیارها رتبه می‌دهد و اصلاً `budget` را نمی‌خواند؛ سنجش رتبه‌ای برای
> هزینه همیشه صفر برمی‌گرداند. آنچه افزایش هزینه واقعاً تهدید می‌کند، جای
> پروژه در سبد است.

همچنین **آزمون ورود و حذف پروژه** انجام می‌شود: رتبه‌بندی با حذف تک‌تک
پروژه‌ها بازاجرا شده و بررسی می‌شود آیا ترتیب بقیه عوض می‌شود (رتبه‌برگشتی).

## ۱۰. کنترل کیفیت داده

`backend/src/domain/data-quality.js`

ماژول **گزارش می‌دهد، ترمیم نمی‌کند**. پر کردن خودکار یک هزینه یا امتیاز مفقود
دقیقاً همان کاری است که شیوه‌نامه انجامش را برای مدل زبانی ممنوع کرده
(«اطلاعات مفقود را حدس بزند») و همان قاعده بر کد هم حاکم است.

سه دسته یافته: **نقص** (پاسخ الزامی ثبت‌نشده، امتیاز موجود نیست، داده‌های
لازم پروژه نیمه‌تمام)، **مغایرت** (جریان نقدی ناسازگار با هزینه تکمیل، مجموع
سهم منابع ≠ ۱۰۰٪، پیشرفت ناسازگار) و **داده نامعتبر** (طبقه ناشناخته، امتیاز
خارج از بازه، بودجه نامعتبر، وابستگی به پروژه ناموجود).

وقتی امتیاز سطح معیار موجود نباشد، موتور از امتیاز سطح بعد استفاده می‌کند اما
این جایگزینی **ثبت و گزارش** می‌شود؛ تصمیمی که با عددی دفاع شود که کسی وارد
نکرده، همان حالت شکستی است که این ماژول برای جلوگیری از آن وجود دارد.

## ۱۱. جایگاه مدل زبانی

`backend/src/services/ai-governance.service.js`

### مجاز (فقط کمکی)

استخراج بندهای مرتبط از اسناد بالادستی · پیشنهاد اولیه معیارها · تطبیق اولیه
پروژه‌ها با اهداف راهبردی · خلاصه‌سازی پیشنهادهای پروژه · شناسایی تعارض یا نقص
در شناسنامه پروژه · استخراج موجودیت‌ها · تولید توضیح قابل‌فهم برای نتایج مدل

### ممنوع بدون تأیید انسانی

تصویب شاخص رسمی · حدس زدن اطلاعات مفقود · تعیین امتیاز قطعی پروژه · حذف
پروژه · اتخاذ تصمیم نهایی سبد

**این ممنوعیت‌ها با پرامپت اعمال نمی‌شوند.** پرامپت یک درخواست است. اعمال
واقعی این است که **هیچ مسیر کدی در لایه AI به امتیاز، معیار، وضعیت پروژه یا
سبد نمی‌نویسد**. مدل هیچ ابزاری، هیچ دسترسی پایگاه‌داده و هیچ دسترسی فایلی
ندارد؛ بنابراین بدترین نتیجه یک تزریق پرامپت موفق، یک پاراگراف گمراه‌کننده در
انتظار رد کارشناس است.

### پرونده اصالت هر خروجی

هر خروجی مدل با این فیلدها ثبت می‌شود: منبع و دامنه · متن پشتیبان · نسخه مدل ·
تاریخ و زمان پردازش · میزان اطمینان · وضعیت تأیید کارشناس · سابقه اصلاح · نام
تأییدکننده · دلیل پذیرش یا رد.

`appliedToDecision` تا لحظه پذیرش کارشناس `false` است. اصلاح کارشناس، خروجی
اصلی مدل را بازنویسی نمی‌کند؛ در `revisions` ثبت می‌شود.

## ۱۲. تطبیق با سند امنیت

| بند سند امنیت | پیاده‌سازی |
|---|---|
| اعتبارسنجی ورودی (لیست سفید) | `validators/*` — همه اسکیماها `.strict()`، کلید وزن از مدل معیارها، شناسه پروژه با الگوی ثابت |
| مدیریت رازها | `config/env.js` — بدون راز در کد؛ تولید بدون `AUTH_SECRET` بالا نمی‌آید؛ `describe()` فقط شکل پیکربندی را گزارش می‌کند |
| احراز هویت و کنترل دسترسی | `middleware/auth.middleware.js` + `config/roles.js` — RBAC مبتنی بر مجوز، ABAC منطقه‌ای، انقضای نشست، مقایسه زمان‌ثابت امضا |
| رفتار امن در حالت خطا | `middleware/error.middleware.js` — بدون stack trace در هیچ محیطی، پیام عمومی برای خطای ۵xx، پاک‌سازی الگوهای نشت |
| محافظ‌های LLM | `security/guardrails.js` — غربال تزریق پرامپت، حذف PII، تشخیص افشای system prompt |
| حداقل دسترسی عامل AI | `context-builder.service.js` — دامنه داده به ازای هر وظیفه؛ مدل بدون ابزار |
| Human-in-the-Loop | `ai-governance.service.js` — مجوز `ai:review` جدا از `ai:use` |
| الگ‌گذاری غیرقابل تغییر | `services/audit.service.js` — زنجیره هش HMAC، بدون مسیر ویرایش یا حذف در API |
| محدودسازی نرخ | `middleware/rate-limit.middleware.js` — سقف درخواست + سقف توکن روزانه |
| اعتماد صفر (CORS) | `app.js` — فهرست سفید مبدأ؛ `cors()` بی‌پارامتر حذف شد |

## ۱۳. برندینگ و محل ویرایش

نام شرکت، نام محصول، نام کارفرما و متن کپی‌رایت در دو فایل متمرکز شده‌اند و
هیچ‌جای دیگری hardcode نشده‌اند:

| فایل | دامنه |
|---|---|
| `backend/src/config/branding.js` | بنر راه‌اندازی، پاسخ ریشه API، جلد و پاورقی گزارش‌های PDF/Excel/PowerPoint، متادیتای فایل‌ها، پرامپت دستیار |
| `front/src/config/branding.ts` | نوار کناری، سربرگ گزارش، نام فایل خروجی |

هر دو فایل دوزبانه‌اند: هر برچسب دو شکل `fa` و `en` دارد. هنگام افزودن برچسب
جدید **هر دو** را وارد کنید و هرگز مقدار `fa` را با متن انگلیسی جایگزین نکنید.

در فرانت‌اند، نمایش هر رشته باید از تابع `t(fa, en)` در `contexts/AppContext`
عبور کند تا تغییر زبان کار کند.

## ۱۴. اتصال به مدل زبانی

اتصال، وابسته به فروشنده خاصی نیست. کتابخانه کلاینت با API سازگار با استاندارد
رایج صحبت می‌کند، بنابراین همان کد با سرویس میزبانی‌شده، یا با استقرار داخلی
(vLLM، Ollama، LM Studio یا دروازه داخلی) کار می‌کند.

| متغیر محیطی | کاربرد |
|---|---|
| `LLM_API_KEY` | کلید دسترسی. خالی بگذارید تا سامانه بدون دستیار کار کند. |
| `LLM_MODEL` | نام مدل. |
| `LLM_BASE_URL` | نشانی سرویس. برای استقرار داخلی و خروج‌نکردن داده از شبکه، این را تنظیم کنید. |

نام‌های قدیمی `OPENAI_*` همچنان پذیرفته می‌شوند تا فایل `.env` موجود از کار
نیفتد؛ اما نام‌های `LLM_*` ارجح هستند.

تنها جایی که SDK نمونه‌سازی می‌شود `backend/src/providers/llm.provider.js` است.
برای تعویض فروشنده، فقط بدنه `createChatCompletion` در همان فایل تغییر می‌کند؛
هیچ ماژول دیگری نمی‌داند کدام فروشنده در حال استفاده است.

## ۱۵. اجرای محلی و لایه نشست

همه مسیرهای `/api/v1` نیازمند نشست معتبر هستند؛ بنابراین فرانت‌اند پیش از
دریافت هر داده‌ای باید نشست بگیرد. این کار در `front/src/contexts/AuthContext.tsx`
و تنها در همان فایل انجام می‌شود.

| محیط | رفتار |
|---|---|
| توسعه | نشست به‌صورت خودکار از `POST /api/v1/auth/session` گرفته می‌شود تا توسعه‌دهنده بدون گام ورود، سامانه را ببیند. |
| تولید | هیچ نشستی صادر نمی‌شود؛ صفحه «ورود به سامانه لازم است» نمایش داده می‌شود و مسیر صدور نشست در بکند با کد ۵۰۱ پاسخ می‌دهد. |

توکن در متغیر ماژول `services/api.ts` نگهداری می‌شود، نه در `localStorage`؛
بنابراین با هر بارگذاری کامل صفحه نشست تازه گرفته می‌شود. به همین دلیل سقف
نرخ مسیر صدور نشست در محیط توسعه بازتر است و در تولید تنگ می‌ماند.

**اجرا:**

```
cd backend && npm start      # روی پورت ۴۰۰۰
cd front   && npm run dev    # روی ۵۱۷۳ و در صورت اشغال بودن، ۵۱۷۴ به بعد
```

سرور توسعه باید از داخل پوشه `front` اجرا شود؛ در غیر این صورت
`front/vite.config.ts` بارگذاری نمی‌شود، پروکسی `/api` غیرفعال می‌ماند و همه
درخواست‌ها با خطای ۴۰۴ برمی‌گردند.

نقش پیش‌فرض نشست توسعه `manager` است. برای بررسی رفتار رابط کاربری با نقش
محدودتر، متغیر `VITE_DEV_ROLE` را تنظیم کنید (برای نمونه `VITE_DEV_ROLE=viewer`).

## ۱۶. نقاط باز

مواردی که آگاهانه در دامنه این نسخه نیستند و پیش از تولید باید تکمیل شوند:

1. **ارائه‌دهنده هویت.** `routes/auth.routes.js` نشست صادر می‌کند اما هویت را
   تأیید نمی‌کند؛ در محیط تولید عمداً غیرفعال است. جای OAuth 2.0 / OIDC
   سازمانی همین‌جاست و تعویض آن فقط همین فایل را تغییر می‌دهد.
2. **پایداری داده.** مخازن روی داده محلی کار می‌کنند؛ لایه `repositories/*`
   درز تعویض با پایگاه داده شهرداری است.
3. **الگ متمرکز.** زنجیره هش، دستکاری را **قابل تشخیص** می‌کند اما فایل محلی
   را غیرقابل تغییر نمی‌کند؛ این کار مقصد الگ مرکزی (WORM) است.
4. **مقیاس افقی.** فروشگاه محدودسازی نرخ و بودجه توکن درون‌فرایندی است و برای
   چند نمونه باید به Redis منتقل شود.
5. **بهینه‌سازی دقیق.** الگوریتم فعلی فراابتکاری است. برای اندازه‌های بزرگ‌تر
   یا الزام اثبات بهینگی، حل با MILP جایگزین مناسبی است؛ ساختار محدودیت‌ها
   برای این تعویض آماده است.
